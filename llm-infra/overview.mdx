LLM infrastructure decisions have a massive impact on cost, latency, and quality. Whether you're routing queries across multiple models, managing context windows at scale, or deciding whether to self-host, the choices you make early define your system's ceiling — this section covers the decisions that matter most in production.

## Managed API vs Self-Hosted

Choosing between a managed API and self-hosted inference is the first architectural fork in any LLM system. Neither is universally better — the right answer depends on your constraints.

<CardGroup cols={2}>
  <Card title="Managed APIs" icon="cloud">
    **Providers:** OpenAI, Anthropic, Google Vertex AI

    - Fastest path to production — no infra to manage
    - Access to the latest frontier models on day one
    - Scales automatically with demand
    - **Trade-offs:** Data leaves your infrastructure, expensive at high volume, limited customization, subject to provider rate limits
  </Card>
  <Card title="Self-Hosted Inference" icon="server">
    **Tools:** vLLM, Ollama, Text Generation Inference (TGI)

    - Full control over data — stays in your VPC or on-prem
    - Significant cost reduction at scale (pay for compute, not per token)
    - Tune serving parameters for your traffic patterns
    - **Trade-offs:** Ops overhead, GPU procurement, model management, your team owns reliability
  </Card>
</CardGroup>

### Decision Framework

Use this checklist to guide your decision:

- **Data sensitivity** — Does your use case involve PII, PHI, or confidential IP? Self-hosted or private cloud deployments are often required for compliance.
- **Scale** — At low request volume, managed APIs are almost always cheaper when you factor in engineering time. Above a certain token volume, self-hosted GPU compute wins on unit economics.
- **Latency requirements** — Managed APIs have network round-trip overhead. A self-hosted model on the same network as your application can be meaningfully faster.
- **Team capacity** — Running GPU inference infrastructure requires MLOps expertise. Don't underestimate the operational burden if your team hasn't done it before.

<Tip>
  A common production pattern is to use managed APIs for early-stage products and frontier-model tasks, while running open-source models on your own infrastructure for high-volume, lower-complexity workloads.
</Tip>

## Model Selection

Not every task needs a frontier model. Matching model capability to task complexity is one of the highest-leverage cost and latency optimizations available to you.

### Frontier Models

| Model | Provider | Best For |
|---|---|---|
| GPT-4o | OpenAI | Complex reasoning, multimodal tasks, agentic workflows |
| Claude 3.5 Sonnet | Anthropic | Long-context analysis, coding, nuanced instruction following |
| Gemini 1.5 Pro | Google | Very long context windows (1M tokens), multimodal |

Frontier models offer the best quality across nearly all benchmarks. Reserve them for tasks where quality directly affects user outcomes or business value.

### Mid-Tier Models

| Model | Provider | Best For |
|---|---|---|
| GPT-4o-mini | OpenAI | Classification, extraction, summarization at scale |
| Claude 3.5 Haiku | Anthropic | Fast, cheap responses with strong instruction following |
| Gemini 1.5 Flash | Google | Low-latency, high-throughput applications |

Mid-tier models offer an excellent quality-to-cost ratio. For many production workloads, they're indistinguishable from frontier models in perceived output quality.

### Open-Source Models

| Model | Parameters | Best For |
|---|---|---|
| Llama 3.1 / 3.2 | 3B–405B | General-purpose, fine-tuning, on-prem deployment |
| Qwen2.5 | 0.5B–72B | Strong multilingual and coding performance |
| Mistral / Mixtral | 7B–8x22B | Efficient inference, European data residency |

Open-source models are self-hostable and can be fine-tuned on your domain data. At the 70B+ scale, they approach frontier model quality on many tasks.

## Cost Optimization Strategies

### Route Queries by Complexity

The single most impactful cost optimization is avoiding expensive models for simple tasks. A classification or keyword extraction task doesn't need GPT-4o — it needs the cheapest model that produces a reliable result.

```python title="LLM Router Pattern"
from openai import OpenAI
from enum import Enum

client = OpenAI()

class QueryComplexity(str, Enum):
    SIMPLE = "simple"      # classification, extraction, yes/no
    MODERATE = "moderate"  # summarization, Q&A, translation
    COMPLEX = "complex"    # reasoning, code gen, long-form synthesis

MODEL_MAP = {
    QueryComplexity.SIMPLE: "gpt-4o-mini",
    QueryComplexity.MODERATE: "gpt-4o-mini",
    QueryComplexity.COMPLEX: "gpt-4o",
}

def classify_query(query: str) -> QueryComplexity:
    """Use a cheap model to decide which model to use."""
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {
                "role": "system",
                "content": (
                    "Classify the complexity of this query as one of: "
                    "simple, moderate, complex. Reply with only the word."
                ),
            },
            {"role": "user", "content": query},
        ],
        temperature=0,
        max_tokens=10,
    )
    label = response.choices[0].message.content.strip().lower()
    return QueryComplexity(label)

def routed_completion(query: str) -> str:
    complexity = classify_query(query)
    model = MODEL_MAP[complexity]
    print(f"Routing to: {model} (complexity: {complexity})")

    response = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": query}],
        temperature=0.2,
    )
    return response.choices[0].message.content
```

### Cache LLM Responses

Semantic caching uses vector similarity to return cached responses for queries that are semantically equivalent — even if the exact wording differs. This is especially effective for FAQ-style applications and documentation chatbots.

<Info>
  Tools like **GPTCache** and **Qdrant** make semantic caching straightforward to implement. A cache hit rate of 20–30% is common in production chatbots, which translates directly to cost savings.
</Info>

### Manage Context Windows

Every token in your prompt costs money. Strategies to reduce prompt size:

- **Summarize conversation history** rather than passing the full transcript
- **Retrieve only the most relevant chunks** in RAG pipelines — don't pad with extra context
- **Use prompt compression tools** like LLMLingua to reduce prompt token count with minimal quality loss
- **Set `max_tokens` explicitly** to avoid runaway completions on simple tasks

### Use Streaming

Streaming doesn't reduce your token cost, but it dramatically improves perceived latency — the first token appears almost immediately rather than waiting for the full response. For user-facing applications, streaming is almost always worth implementing.
