Self-hosting LLMs gives you control over costs, data privacy, and model customization that managed APIs simply can't match. The tradeoff is operational complexity — but tools like vLLM and Ollama have made it dramatically more accessible. This page covers the two most practical options for most teams: vLLM for production GPU inference and Ollama for local development.

## vLLM: High-Throughput Production Inference

[vLLM](https://github.com/vllm-project/vllm) is the de-facto standard for serving open-source LLMs in production. It was built from the ground up for high-throughput, low-latency inference — not as an afterthought.

**What makes vLLM fast:**

- **PagedAttention** — manages GPU KV cache memory in pages (similar to virtual memory in an OS), eliminating memory fragmentation and allowing much higher batch sizes
- **Continuous batching** — new requests join in-flight batches dynamically, maximizing GPU utilization without waiting for a batch to complete
- **OpenAI-compatible REST API** — drop-in replacement for OpenAI's API endpoint, so your existing client code works unchanged

### Installation and Startup

<Steps>
  <Step title="Install vLLM">
    ```bash title="Install vLLM"
    pip install vllm
    ```
    vLLM requires a CUDA-capable GPU. For multi-GPU setups, ensure your NCCL and CUDA versions are compatible. Check the [vLLM installation docs](https://docs.vllm.ai/en/latest/getting_started/installation.html) for version requirements.
  </Step>
  <Step title="Start the inference server">
    ```bash title="Start vLLM Server"
    python -m vllm.entrypoints.openai.api_server \
      --model Qwen/Qwen2.5-7B-Instruct \
      --tensor-parallel-size 1 \
      --max-model-len 8192 \
      --port 8000
    ```
    The server will download the model from Hugging Face on first run (or use a locally cached copy). Once ready, it exposes an OpenAI-compatible API at `http://localhost:8000/v1`.
  </Step>
  <Step title="Make your first request">
    ```python title="Call vLLM with the OpenAI Client"
    from openai import OpenAI

    client = OpenAI(
        base_url="http://localhost:8000/v1",
        api_key="not-needed"  # vLLM doesn't require auth by default
    )

    response = client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct",
        messages=[{"role": "user", "content": "Explain RAG in one paragraph."}],
        temperature=0.1
    )
    print(response.choices[0].message.content)
    ```
    Because vLLM speaks the OpenAI API protocol, you can point any OpenAI-compatible library at it by changing `base_url` — no other code changes needed.
  </Step>
</Steps>

### Key Configuration Options

| Flag | Description | Example |
|---|---|---|
| `--tensor-parallel-size` | Number of GPUs to shard the model across | `--tensor-parallel-size 2` for 2 GPUs |
| `--max-model-len` | Maximum sequence length (prompt + completion) | `--max-model-len 16384` |
| `--quantization` | Quantization format to use | `--quantization awq` |
| `--gpu-memory-utilization` | Fraction of GPU VRAM for the model | `--gpu-memory-utilization 0.90` |
| `--dtype` | Weight dtype (`float16`, `bfloat16`, `auto`) | `--dtype bfloat16` |

### Quantization

Quantization reduces model weight precision to fit larger models into available GPU VRAM, with varying degrees of quality trade-off.

<CardGroup cols={3}>
  <Card title="AWQ" icon="circle-check" href="https://huggingface.co/docs/transformers/quantization/awq">
    **Activation-aware Weight Quantization.** 4-bit quantization with minimal quality degradation. The best default choice for production — use `--quantization awq` with an AWQ-quantized model checkpoint.
  </Card>
  <Card title="GPTQ" icon="circle-half-stroke" href="https://huggingface.co/docs/transformers/quantization/gptq">
    **Post-training quantization** to 4-bit or 8-bit. Slightly higher quality loss than AWQ but widely available for most open-source models. Use `--quantization gptq`.
  </Card>
  <Card title="BitsAndBytes" icon="circle-xmark" href="https://huggingface.co/docs/transformers/quantization/bitsandbytes">
    **Dynamic quantization** — quantizes weights at load time. Slowest inference of the three but requires no pre-quantized checkpoint. Best for experimentation, not production throughput.
  </Card>
</CardGroup>

<Tip>
  AWQ-quantized checkpoints for popular models (Llama, Qwen, Mistral) are widely available on Hugging Face under the `TheBloke` and official org namespaces. Running a 70B AWQ model on a single 80GB A100 is entirely feasible.
</Tip>

## Ollama: Local Development

[Ollama](https://ollama.com) is the fastest way to run open-source models on your local machine — macOS, Linux, or Windows. It handles model downloads, runtime configuration, and exposes a local API server automatically.

### Pull and Run Models

```bash title="Ollama Quickstart"
# Pull a model (downloads once, cached locally)
ollama pull llama3.2:3b

# Run it interactively in your terminal
ollama run llama3.2:3b

# The REST API is available at http://localhost:11434
# (starts automatically when you run any model)
```

Ollama uses [GGUF](https://github.com/ggerganov/ggml/blob/master/docs/gguf.md) quantized models, which run efficiently on CPU or Apple Silicon GPU (Metal). For development and prototyping, a 3B–8B model runs comfortably on a modern laptop.

### Use with LangChain

```python title="Ollama + LangChain"
from langchain_ollama import ChatOllama

llm = ChatOllama(model="llama3.2:3b", temperature=0)
response = llm.invoke("Explain embeddings in one paragraph.")
print(response.content)
```

Switching between Ollama (local) and a managed provider in LangChain is a one-line change — just swap the LLM class. This makes it easy to develop locally and deploy against OpenAI or a vLLM server in production.

### Customize with a Modelfile

A `Modelfile` lets you create a custom variant of any base model — setting a system prompt, adjusting temperature, or changing the context window:

```dockerfile title="Modelfile"
FROM llama3.2:3b

# Set a persistent system prompt
SYSTEM """
You are a senior software engineer specializing in Python and distributed systems.
Be concise. Prefer code examples over prose.
"""

# Override default parameters
PARAMETER temperature 0.1
PARAMETER num_ctx 4096
PARAMETER top_p 0.9
```

```bash title="Build and Run Custom Model"
ollama create my-engineer -f Modelfile
ollama run my-engineer
```

## LiteLLM: Unified Multi-Provider Proxy

When you're running both managed APIs and self-hosted vLLM endpoints, [LiteLLM](https://github.com/BerriAI/litellm) acts as a unified proxy layer that abstracts them all behind one OpenAI-compatible API. It adds provider failover, load balancing, and cost tracking with minimal configuration.

### Deploy as a Proxy Server

```yaml title="litellm_config.yaml"
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY

  - model_name: claude-sonnet
    litellm_params:
      model: anthropic/claude-3-5-sonnet-20241022
      api_key: os.environ/ANTHROPIC_API_KEY

  - model_name: qwen-local
    litellm_params:
      model: openai/Qwen/Qwen2.5-7B-Instruct
      api_base: http://localhost:8000/v1
      api_key: not-needed

router_settings:
  routing_strategy: least-busy
  num_retries: 3
  fallbacks:
    - gpt-4o:
        - claude-sonnet
        - qwen-local
```

```bash title="Start LiteLLM Proxy"
pip install 'litellm[proxy]'
litellm --config litellm_config.yaml --port 4000
```

Your application points at `http://localhost:4000` and uses standard OpenAI client code — the proxy handles provider selection, retries, and usage tracking transparently.

```python title="Route Requests Through LiteLLM Proxy"
from openai import OpenAI

# All requests go through the LiteLLM proxy
client = OpenAI(
    base_url="http://localhost:4000",
    api_key="your-litellm-master-key",
)

response = client.chat.completions.create(
    model="gpt-4o",   # Resolved by LiteLLM router
    messages=[{"role": "user", "content": "Explain PagedAttention."}],
)
print(response.choices[0].message.content)
```

### LiteLLM vs Direct Client Calls

| Concern | Direct Client | LiteLLM Proxy |
|---|---|---|
| Provider failover | Manual | Automatic |
| Cost tracking | Per-provider dashboard | Unified |
| Load balancing across replicas | Custom code | Built-in |
| A/B testing models | Custom code | Config-driven |
| Rate limit handling | Manual retry logic | Automatic |

<Note>
  LiteLLM is especially valuable in multi-tenant SaaS products where you want to route different tenant plans to different models (free tier → `gpt-4o-mini`, enterprise → `gpt-4o`) while keeping application code unchanged. See the [SaaS Architecture](/llm-infra/saas-architecture) page for tenant-aware routing patterns.
</Note>

## LLM Observability

Running LLMs in production without observability is flying blind. You need visibility into what prompts are being sent, what responses come back, how long things take, and how much it costs.

### LangSmith

[LangSmith](https://smith.langchain.com) is the most complete tracing solution if you're using LangChain. It captures every step of your chain execution — prompts, retrieved documents, tool calls, and completions — with minimal setup.

```python title="Enable LangSmith Tracing"
import os

os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "your-api-key"
os.environ["LANGCHAIN_PROJECT"] = "my-project"

# All LangChain calls in this process are now traced automatically
```

Once tracing is enabled, every LangChain invocation appears in your LangSmith dashboard with full input/output visibility, latency breakdowns, and token counts — no code changes required beyond setting the environment variables.

### Key Metrics to Track

| Metric | Why It Matters |
|---|---|
| **Latency (p50/p95/p99)** | User experience; identify slow prompts or overloaded models |
| **Token usage (prompt + completion)** | Primary cost driver for managed APIs |
| **Cost per request** | Aggregate view of spend by endpoint, user, or feature |
| **Error rate** | Rate limit hits, timeouts, malformed outputs |
| **Cache hit rate** | Effectiveness of semantic caching layer |

<Info>
  For non-LangChain workloads, OpenTelemetry-based tracing with tools like **OpenLLMetry** or **Langfuse** gives you vendor-neutral observability. Both support custom spans so you can trace exactly the layers that matter in your architecture.
</Info>

## Inference Optimization Tips

<AccordionGroup>
  <Accordion title="KV Cache Memory Planning">
    The KV (key-value) cache stores attention state for tokens already processed, enabling efficient autoregressive generation. It lives in GPU VRAM alongside model weights.

    Before deploying, estimate your KV cache memory requirement:
    ```text title="KV Cache Formula"
    KV cache size ≈ 2 × num_layers × num_heads × head_dim × max_seq_len × batch_size × dtype_bytes
    ```
    If your model weights use 20GB of VRAM and your GPU has 24GB total, you have only 4GB for KV cache — which constrains your max sequence length and concurrent request capacity. Plan this before you hit OOM errors in production.
  </Accordion>
  <Accordion title="Continuous Batching">
    Traditional batching waits for a full batch before processing — wasteful when requests arrive at irregular intervals. vLLM's **continuous batching** (also called iteration-level scheduling) adds new requests to in-flight batches dynamically.

    You don't need to configure this — it's on by default in vLLM. But it's why vLLM's GPU utilization is so much higher than naive serving setups. Tune `--max-num-seqs` (max concurrent sequences) to match your GPU's capacity.
  </Accordion>
  <Accordion title="Quantization Trade-offs">
    Quantization precision and quality loss follow a predictable pattern:

    | Format | Bits | VRAM vs FP16 | Quality Loss |
    |---|---|---|---|
    | FP16 / BF16 | 16 | 1× (baseline) | None |
    | GPTQ / AWQ | 4 | ~0.35× | Low (AWQ) / Medium (GPTQ) |
    | INT8 | 8 | ~0.5× | Very low |
    | INT4 | 4 | ~0.25× | Medium |

    **AWQ** is the recommended default for production quantization — it selects which weights to quantize based on activation magnitude, preserving the most impactful weights at higher precision. On most tasks, AWQ-4bit quality is within 1–2% of FP16.
  </Accordion>
  <Accordion title="CPU Offloading for Large Models">
    If your model is too large for GPU VRAM, you can offload some layers to CPU RAM (or even NVMe via llama.cpp). This makes it possible to run 70B+ models on consumer hardware, at the cost of significantly lower throughput.

    In vLLM, use `--cpu-offload-gb` to specify how many gigabytes of model weights to offload to CPU:
    ```bash title="CPU Offload in vLLM"
    python -m vllm.entrypoints.openai.api_server \
      --model meta-llama/Llama-3.1-70B-Instruct \
      --cpu-offload-gb 20 \
      --gpu-memory-utilization 0.95
    ```
    CPU offloading is not suitable for latency-sensitive production workloads. Use it for batch processing or experimentation where throughput is more important than response time.
  </Accordion>
</AccordionGroup>
