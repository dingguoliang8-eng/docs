A single agent with access to many tools eventually hits a wall: the context window fills up, task complexity outgrows what one planning loop can manage, and debugging becomes a nightmare. **Multi-agent systems** solve this by decomposing work across specialized agents that each own a narrow domain. The benefits are practical — smaller context windows, parallelism, independent failure isolation — but the tradeoffs are real. Understanding the topologies and knowing when to use (or avoid) them is the most important skill here.

---

## Multi-Agent Topologies

### 1. Supervisor / Orchestrator

A single **supervisor** agent receives the user's task, decides which specialist agent to call, passes it the relevant sub-task, and synthesizes the results. Workers have no awareness of each other; all coordination flows through the supervisor.

```text
User → Supervisor → [Research Agent | Coding Agent | Writing Agent] → Supervisor → User
```

**Best for:** Tasks with clear, separable sub-domains where you need a single point of routing control.

### 2. Hierarchical

Nested supervisors handle increasingly fine-grained delegation. A top-level supervisor routes to mid-level supervisors, each of which manages its own pool of specialists.

```text
User → Top Supervisor → [Research Supervisor → [Web Agent | DB Agent]]
                      → [Code Supervisor   → [Writer Agent | Tester Agent]]
```

**Best for:** Enterprise-scale workflows where a flat supervisor would need to reason about too many agents at once.

<Warning>
  Hierarchical systems are expensive to debug. Each layer adds latency, and a miscommunication at the top level silently corrupts everything downstream. Build and validate the flat supervisor version first, then add hierarchy only when you have a concrete scalability reason.
</Warning>

### 3. Peer-to-Peer (Swarm)

Agents communicate directly without a central coordinator. Each agent can hand off control to any other agent based on the current context. LangGraph's `langgraph-swarm` package implements this pattern with a shared message history and a `handoff` tool.

```text
Agent A ←→ Agent B ←→ Agent C  (any agent can pass control to any other)
```

**Best for:** Workflows where task ownership naturally shifts between specialists mid-execution (e.g., a triage agent handing off to a domain expert, who hands back for final formatting).

## Supervisor Pattern with LangGraph

The most practical place to start. Here you'll build a supervisor that routes between a **research agent** and a **coding agent**, then synthesizes their outputs.

### Defining Worker Agents

Each worker is its own compiled LangGraph graph — or a simple chain. The supervisor calls them as tools.

```python agents/multi_agent/workers.py
from langchain_openai import ChatOpenAI
from langchain_community.tools.tavily_search import TavilySearchResults
from langgraph.prebuilt import create_react_agent

llm = ChatOpenAI(model="gpt-4o", temperature=0)

# Research specialist: web search only
research_agent = create_react_agent(
    llm,
    tools=[TavilySearchResults(max_results=5)],
    state_modifier="You are a research specialist. Find accurate, up-to-date information.",
)

# Coding specialist: Python REPL only
from langchain_experimental.tools.python.tool import PythonREPLTool

coding_agent = create_react_agent(
    llm,
    tools=[PythonREPLTool()],
    state_modifier="You are a coding specialist. Write clean, well-commented Python code.",
)
```

### Supervisor Routing with Structured Output

The supervisor uses **structured output** to emit a deterministic routing decision rather than free text.

```python agents/multi_agent/supervisor.py
from typing import Literal
from pydantic import BaseModel
from langchain_openai import ChatOpenAI

WORKERS = ["researcher", "coder", "FINISH"]

class RouteDecision(BaseModel):
    """Routing decision returned by the supervisor."""
    next: Literal["researcher", "coder", "FINISH"]
    reasoning: str

llm = ChatOpenAI(model="gpt-4o", temperature=0)
router_llm = llm.with_structured_output(RouteDecision)

SUPERVISOR_PROMPT = """You are a supervisor coordinating a research agent and a coding agent.
Given the conversation so far, decide which agent should act next, or FINISH if the task is complete.

Workers:
- researcher: finds information, searches the web, retrieves facts
- coder: writes and executes Python code, performs calculations
- FINISH: the task is fully complete and a final answer is ready

Always reason before deciding."""

def supervisor_node(state: dict) -> dict:
    messages = [{"role": "system", "content": SUPERVISOR_PROMPT}] + state["messages"]
    decision = router_llm.invoke(messages)
    return {"next": decision.next, "reasoning": decision.reasoning}
```

### Assembling the Supervisor Graph

```python agents/multi_agent/graph.py
from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class SupervisorState(TypedDict):
    messages: Annotated[list, add_messages]
    next: str
    reasoning: str

def make_worker_node(agent, name: str):
    """Wrap a worker agent as a graph node."""
    def node(state: SupervisorState) -> dict:
        result = agent.invoke({"messages": state["messages"]})
        # Tag the final message with the worker's name for traceability
        last = result["messages"][-1]
        last.name = name
        return {"messages": [last]}
    return node

builder = StateGraph(SupervisorState)

# Add nodes
builder.add_node("supervisor", supervisor_node)
builder.add_node("researcher", make_worker_node(research_agent, "researcher"))
builder.add_node("coder", make_worker_node(coding_agent, "coder"))

# Supervisor always runs first
builder.add_edge(START, "supervisor")

# Conditional routing from supervisor
def route(state: SupervisorState) -> str:
    return END if state["next"] == "FINISH" else state["next"]

builder.add_conditional_edges("supervisor", route)

# Workers always return to supervisor
builder.add_edge("researcher", "supervisor")
builder.add_edge("coder", "supervisor")

graph = builder.compile()
```

### Running the Supervisor

```python agents/multi_agent/run.py
from langchain_core.messages import HumanMessage

result = graph.invoke({
    "messages": [HumanMessage(
        content="Research the latest Python version, then write a script that prints its release date."
    )],
    "next": "",
    "reasoning": "",
})

for message in result["messages"]:
    sender = getattr(message, "name", message.__class__.__name__)
    print(f"[{sender}]: {message.content[:200]}")
```

## Shared State and Communication

Agents in a multi-agent system need to exchange information. LangGraph gives you three mechanisms:

### State Passing (Recommended)

The supervisor graph's `messages` field acts as shared memory. Every worker appends its output to the message list, so the supervisor — and subsequent workers — see the full context.

```python agents/multi_agent/state_passing.py
# Workers return their output as a message; the supervisor reads all prior messages
def researcher_node(state: SupervisorState) -> dict:
    result = research_agent.invoke({"messages": state["messages"]})
    return {"messages": result["messages"]}  # appended via add_messages reducer
```

### Subgraph State Sharing

When workers are full LangGraph subgraphs, you can share state keys between the parent and child graph by overlapping their schemas.

```python agents/multi_agent/subgraph_state.py
class SharedState(TypedDict):
    messages: Annotated[list, add_messages]
    # This field is visible to both parent and any subgraph that declares it
    search_results: list[str]
```

### External Memory (Long-Term)

For state that must persist across multiple multi-agent runs, write to an external store and retrieve it at the start of each run.

```python agents/multi_agent/external_memory.py
import json
import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def load_session_context(session_id: str) -> list:
    raw = r.get(f"session:{session_id}:context")
    return json.loads(raw) if raw else []

def save_session_context(session_id: str, messages: list):
    r.set(f"session:{session_id}:context", json.dumps(messages), ex=3600)
```

## Practical Considerations

### When NOT to Use Multi-Agent

Multi-agent systems add real complexity. Before reaching for them, check whether a simpler approach would work:

- **Single agent + more tools**: Most tasks that seem to need multiple agents can be handled by one well-prompted agent with the right tool set.
- **Single agent + longer context**: If the bottleneck is context length, try summarization or retrieval-augmented memory before splitting into agents.
- **Batch processing**: If tasks are independent, run a single agent in a loop rather than building an orchestration layer.

<Warning>
  Every hop between agents multiplies your latency, token cost, and failure surface. A four-agent pipeline where each agent has a 95% success rate gives you roughly 81% end-to-end reliability — before accounting for network failures or rate limits. Add agents only when the task genuinely requires specialization or parallelism.
</Warning>

### Debugging Multi-Agent Flows

Multi-agent bugs are hard to spot because failures propagate silently through routing decisions. These practices help:

```python agents/multi_agent/debug.py
import logging

logging.basicConfig(level=logging.INFO)

# Log every routing decision
def supervisor_node(state: SupervisorState) -> dict:
    decision = router_llm.invoke(...)
    logging.info(
        f"Supervisor routing to '{decision.next}'. Reason: {decision.reasoning}"
    )
    return {"next": decision.next, "reasoning": decision.reasoning}
```

- **Tag every message** with the agent name that produced it (`.name` attribute).
- **Log routing decisions** at INFO level, including the `reasoning` field.
- **Use LangGraph's `stream_mode="updates"`** to watch node-by-node execution in development.
- **Test each worker in isolation** before plugging it into the supervisor graph.

### Observability with LangSmith

LangSmith traces every node execution, LLM call, and tool invocation across your entire multi-agent graph in a single view.

```python agents/multi_agent/tracing.py
import os

# Set these before importing LangGraph/LangChain
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "ls__..."
os.environ["LANGCHAIN_PROJECT"] = "multi-agent-supervisor"

# Now all graph invocations are automatically traced — no code changes needed
result = graph.invoke({"messages": [HumanMessage(content="...")]})
```

LangSmith lets you replay individual traces, inspect intermediate states, and compare runs side-by-side — essential when diagnosing why the supervisor made an unexpected routing decision.
