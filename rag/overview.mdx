Retrieval-Augmented Generation (RAG) augments large language models with external knowledge retrieved at inference time. Instead of relying solely on what a model learned during training, RAG fetches relevant documents from your own data sources and supplies them as context — dramatically reducing hallucination, enabling domain-specific answers, and keeping responses grounded in verifiable content.

## The RAG Pipeline

RAG operates in two distinct phases: **indexing** (a one-time or periodic offline process) and **querying** (a real-time online process triggered by each user request).

<Steps>
  <Step title="Indexing Phase">
    Raw documents are loaded, split into chunks, converted into vector embeddings, and stored in a vector database alongside their metadata.

    ```text
    Documents → Chunker → Embedding Model → Vector Store
    ```
  </Step>
  <Step title="Query Phase">
    The user's query is embedded with the same model, used to retrieve the most relevant chunks, optionally reranked for precision, and then passed — with the original question — to the LLM to synthesize a grounded answer.

    ```text
    Query → Embedding Model → Retriever → Reranker → LLM → Answer
    ```
  </Step>
</Steps>

Putting both phases together, the full data flow looks like this:

```text
  INDEXING
  ─────────
  Raw Docs → Chunker → Embedding Model → Vector Store

  QUERYING
  ────────
  User Query → Embedding Model → Retriever → Reranker → LLM → Answer
```

<Note>
  The quality of your RAG system is bounded first by chunking, second by embeddings, and third by retrieval strategy — before the LLM even enters the picture. Invest heavily in the indexing pipeline.
</Note>

### Basic RAG Pipeline in LangChain

The following example wires together OpenAI embeddings, a Qdrant vector store, and GPT-4o into a functional RAG chain:

```python title="basic_rag.py"
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_qdrant import QdrantVectorStore
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# Indexing
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = QdrantVectorStore.from_documents(
    documents=docs,
    embedding=embeddings,
    url="http://localhost:6333",
    collection_name="knowledge_base"
)

# Retrieval + Generation (LCEL chain)
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
llm = ChatOpenAI(model="gpt-4o")

prompt = ChatPromptTemplate.from_template(
    "Answer the question using only the context below.\n\nContext:\n{context}\n\nQuestion: {question}"
)

def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)
result = rag_chain.invoke("What is our return policy?")
```

## When to Use RAG

RAG is the right choice whenever your application needs to answer questions grounded in a specific corpus of knowledge — especially when that corpus changes over time.

## RAG vs Fine-tuning

Both RAG and fine-tuning adapt a base LLM to your needs, but they solve different problems. Choosing the wrong approach is one of the most common mistakes in AI engineering.

| Dimension | RAG | Fine-tuning |
|---|---|---|
| **Knowledge updates** | ✅ Update the index, no retraining | ❌ Requires a new training run |
| **Grounding / citations** | ✅ Sources are explicit and auditable | ❌ Knowledge is implicit in weights |
| **Data volume needed** | ✅ Works with any corpus size | ❌ Needs high-quality labeled examples |
| **Latency** | ⚠️ Adds retrieval overhead | ✅ Single inference call |
| **Style / tone control** | ⚠️ Prompt engineering required | ✅ Fine-tune directly on target style |
| **Behavior changes** | ⚠️ Difficult to modify base behavior | ✅ Ideal for capability or format changes |
| **Cost** | ✅ No training cost | ❌ Training compute is expensive |

<Info>
  In practice, the best production systems often combine both: fine-tune the model for style and instruction following, then add RAG for domain-specific factual grounding. These techniques are complementary, not mutually exclusive.
</Info>

**Choose RAG when** your knowledge base is large, frequently updated, or when you need transparent citations and auditability.

**Choose fine-tuning when** you need to change how the model behaves, formats its output, or when latency is critical and retrieval overhead is unacceptable.
