朴素 RAG——嵌查询、取 Top-K、生成——上线后很快不够用。真实问题含糊、缺上下文；召回块「相关」但不够 LLM 回答；有时索引里根本没有好答案。下面这些模式按「从简到繁」排，各自对应一类可测的问题。

<Tip>
  先把最简流水线测清楚，再按评估缺口加复杂度。多一层就多延迟、成本和失败点。
</Tip>

## 查询变换

最大的召回失败来源之一是**说法和文档用语对不上**。

- **Query rewriting**：把口语问题改写成适合检索的自包含查询
- **HyDE**：先让模型写一篇「假想答案文档」，再拿它去检索（长文语料更有效）
- **Multi-query**：生成多个语义变体分别检索再去重，提升模糊问题的召回

## 父子检索（Parent-Child）

小块嵌得好、召回准，但上下文不够；大块上下文足，向量又糊。做法：用小 child 块做检索，把对应大 parent 块交给 LLM。

生产里 parent 存 Redis 等持久存储，别用进程内 `InMemoryStore` 硬扛。

## Self-RAG / Corrective RAG

给流水线加反馈：

- **Self-RAG**：是否检索、文档是否相关、答案是否有据，分步判定（常做成 LangGraph 条件边）
- **CRAG**：检索质量不过关时，宁可走网页搜索兜底，也不硬用烂上下文胡编

## 上下文压缩

相关块里仍有废话。用压缩器只留和问题直接相关的句子。注意：每块多一次 LLM 调用，适合在重排后、候选已经很少时用便宜模型。

## 多向量索引

同一源文档可索引多种表示：摘要向量、假想问题向量、结构化事实……检索命中后再回原始全文。

## 一套常见生产组合

1. 查询改写
2. 混合检索（取 20–50）
3. 重排到 5–10
4. （可选）上下文压缩
5. 带引用/拒答的生成
6. （高风险场景）生成后做 faithfulness 检查

<Warning>
  先量基线再加花样。目标是「够准的最简系统」，不是「看起来最炫的系统」。
</Warning>
