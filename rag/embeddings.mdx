Embeddings are the foundation of every RAG system. A vector embedding encodes the semantic meaning of a piece of text as a high-dimensional numeric vector, making it possible to measure similarity between a query and thousands of documents in milliseconds. The quality of your retrieval is fundamentally **bounded by your embedding model** — no amount of prompt engineering or reranking can recover context that was never retrieved in the first place.

## Choosing an Embedding Model

There is no universally "best" embedding model. Your choice depends on your language coverage requirements, context window needs, deployment constraints (API vs self-hosted), and budget.

### Model Comparison

| Model | Dims | Context | Highlights |
|---|---|---|---|
| `text-embedding-3-small` | 1536 | 8191 tokens | Best price/quality ratio for English; easy OpenAI API integration |
| `text-embedding-3-large` | 3072 | 8191 tokens | OpenAI's highest-quality model; strong on MTEB benchmarks |
| `embed-v3` (Cohere) | 1024 | 512 tokens | Best-in-class multilingual; separate `search_document` / `search_query` input types |
| `BGE-M3` (BAAI) | 1024 | 8192 tokens | Open-source; supports dense, sparse, and ColBERT multi-vector simultaneously |
| `E5-large-v2` | 1024 | 512 tokens | Strong English performance; free to self-host; requires instruction prefixes |
| `jina-embeddings-v3` (Jina AI) | 1024 | 8192 tokens | Long-context champion; task-specific LoRA adapters |

<Tip>
  Start with `text-embedding-3-small` for most English-language projects — it hits an excellent balance of quality, latency, and cost. Graduate to `BGE-M3` or `jina-embeddings-v3` when you need long-context support or want to eliminate API costs at scale.
</Tip>

### Initializing Your Embedding Model

<CodeGroup>
```python title="OpenAI Embeddings"
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small",
    dimensions=512  # Matryoshka truncation — reduces cost without big quality loss
)
```

```python title="Cohere Embeddings"
from langchain_cohere import CohereEmbeddings

embeddings = CohereEmbeddings(
    model="embed-english-v3.0",
    input_type="search_document"  # Use "search_query" at query time
)
```

```python title="BGE-M3 (Local)"
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-m3",
    model_kwargs={"device": "cuda"},
    encode_kwargs={"normalize_embeddings": True}
)
```
</CodeGroup>

## Chunking Strategies

Chunking is often **more impactful than the choice of embedding model**. If your chunks are too large, the embedding averages over too much content and loses specificity. If they are too small, you retrieve fragments that lack enough context for the LLM to generate a useful answer.

<Accordion title="Fixed-Size Chunking">
  Split text into chunks of exactly N characters or tokens, with an optional overlap to prevent context from being cut at boundaries. Simple and predictable, but unaware of sentence or paragraph structure.

  **Best for:** homogeneous documents with consistent formatting (logs, structured records).

  ```python title="fixed_chunking.py"
  from langchain_text_splitters import CharacterTextSplitter

  splitter = CharacterTextSplitter(
      chunk_size=512,
      chunk_overlap=64,
      separator="\n"
  )
  chunks = splitter.split_documents(documents)
  ```
</Accordion>

<Accordion title="Recursive Character Splitting (Recommended Default)">
  Tries to split on natural boundaries (`\n\n`, `\n`, `. `, ` `) in order of preference, falling back to character-level only when necessary. Respects sentence and paragraph structure without requiring a parsing library.

  **Best for:** prose documents, README files, help articles, PDFs.

  ```python title="recursive_splitting.py"
  from langchain_text_splitters import RecursiveCharacterTextSplitter

  splitter = RecursiveCharacterTextSplitter(
      chunk_size=512,
      chunk_overlap=64,
      separators=["\n\n", "\n", ". ", " ", ""]
  )
  chunks = splitter.split_documents(documents)
  ```
</Accordion>

<Accordion title="Semantic Chunking">
  Embeds every sentence, then splits whenever the cosine similarity between adjacent sentences drops below a threshold. Creates chunks that are semantically coherent rather than mechanically sized.

  **Best for:** long documents with diverse topics (research papers, book chapters).

  ```python title="semantic_chunking.py"
  from langchain_experimental.text_splitter import SemanticChunker
  from langchain_openai import OpenAIEmbeddings

  splitter = SemanticChunker(
      embeddings=OpenAIEmbeddings(),
      breakpoint_threshold_type="percentile",  # or "standard_deviation"
      breakpoint_threshold_amount=90
  )
  chunks = splitter.split_documents(documents)
  ```
</Accordion>

<Accordion title="Document-Aware Chunking">
  Parses document structure (Markdown headers, HTML tags, code blocks, tables) and respects those boundaries when splitting. Avoids cutting a code block in half or merging content from different sections.

  **Best for:** Markdown documentation, HTML pages, Jupyter notebooks.

  ```python title="markdown_chunking.py"
  from langchain_text_splitters import MarkdownHeaderTextSplitter

  headers_to_split_on = [
      ("#", "h1"),
      ("##", "h2"),
      ("###", "h3"),
  ]
  splitter = MarkdownHeaderTextSplitter(
      headers_to_split_on=headers_to_split_on,
      strip_headers=False
  )
  chunks = splitter.split_text(markdown_document)
  ```
</Accordion>

<Note>
  Always set a non-zero `chunk_overlap` (10–15% of `chunk_size` is a good default). Without overlap, a sentence that straddles a chunk boundary will be semantically split and potentially missed by retrieval.
</Note>

## Vector Stores

Your vector store is responsible for persisting embeddings and executing similarity queries at low latency. Each option has different trade-offs between operational simplicity, performance, and cost.

<CardGroup cols={2}>
  <Card title="Qdrant" icon="database">
    **Recommended for production.** Written in Rust for high throughput. Rich payload filtering, sparse vector support, on-disk indexing, and a convenient Docker image. Supports hybrid search natively.
  </Card>
  <Card title="Chroma" icon="laptop-code">
    **Best for local development.** Zero-config, runs in-process or as a server, and integrates with LangChain in a single line. Not recommended for high-concurrency production workloads.
  </Card>
  <Card title="Pinecone" icon="cloud">
    **Fully managed and serverless.** No infrastructure to operate — ideal if you want to focus on the application layer. Pricing scales with index size and query volume.
  </Card>
  <Card title="pgvector" icon="elephant">
    **Best if you're already on PostgreSQL.** Adds vector similarity search as a Postgres extension. Simplifies your stack if you don't want to operate a separate vector database.
  </Card>
</CardGroup>

### Connecting to Qdrant

```python title="qdrant_setup.py"
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams
from langchain_community.vectorstores import Qdrant

# Create a collection (run once)
client = QdrantClient(url="http://localhost:6333")
client.create_collection(
    collection_name="docs",
    vectors_config=VectorParams(size=1536, distance=Distance.COSINE)
)

# Connect LangChain to the collection
vectorstore = Qdrant(
    client=client,
    collection_name="docs",
    embeddings=embeddings
)

# Index documents
vectorstore.add_documents(chunks)
```

## Embedding Best Practices

<Steps>
  <Step title="Use separate embeddings for queries and documents">
    Models like E5 and BGE are trained with instruction prefixes. Omitting them silently degrades retrieval quality.

    ```python title="instruction_prefixes.py"
    # E5 instruction prefixes
    query_prefix = "query: "
    doc_prefix = "passage: "

    query_embedding = model.encode(query_prefix + user_query)
    doc_embedding = model.encode(doc_prefix + document_text)
    ```
  </Step>
  <Step title="Cache document embeddings aggressively">
    Embedding a large corpus on every deployment is slow and expensive. Persist embeddings to your vector store during an offline indexing job and only re-embed documents that have changed.

    ```python title="incremental_indexing.py"
    import hashlib

    def get_doc_hash(text: str) -> str:
        return hashlib.sha256(text.encode()).hexdigest()

    # Only embed if the hash has changed
    if stored_hash != get_doc_hash(doc.page_content):
        vectorstore.add_documents([doc])
        update_hash(doc.metadata["id"], get_doc_hash(doc.page_content))
    ```
  </Step>
  <Step title="Normalize vectors for cosine similarity">
    Most models output un-normalized vectors. Normalizing to unit length ensures cosine similarity and dot product produce identical results and that distance comparisons are consistent.

    ```python title="normalize.py"
    import numpy as np

    def normalize(vector: list[float]) -> list[float]:
        v = np.array(vector)
        return (v / np.linalg.norm(v)).tolist()
    ```
  </Step>
  <Step title="Monitor for embedding drift">
    If you update your embedding model, older vectors are no longer comparable. Version your collections and schedule a full re-indexing run whenever you change the embedding model.
  </Step>
</Steps>

<Warning>
  Never mix embeddings from different models in the same vector collection. A `text-embedding-3-small` vector and a `BGE-M3` vector occupy fundamentally different geometric spaces — similarity scores between them are meaningless.
</Warning>
