自托管 LLM 能在成本、数据和定制上拿到托管 API 给不了的控制权；代价是运维复杂度。对多数团队，实用组合是：**生产用 vLLM，本地开发用 Ollama**。

## vLLM：生产高吞吐推理

vLLM 几乎是开源模型生产服务的默认选项。快，主要靠：

- **PagedAttention**：KV cache 分页管理，少碎片、更大 batch
- **Continuous batching**：请求动态进批，GPU 利用率更高
- **OpenAI 兼容 API**：现有客户端改 `base_url` 就能切

```bash title="Start vLLM Server"
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --tensor-parallel-size 1 \
  --max-model-len 8192 \
  --port 8000
```

常用旋钮：`--tensor-parallel-size`、`--max-model-len`、`--quantization`、`--gpu-memory-utilization`、`--dtype`。

量化方面，生产默认更倾向 **AWQ**；GPTQ 也常见；BitsAndBytes 更适合试验。

## Ollama：本地开发

拉模型、跑交互、本地 API（默认 `11434`）都很省事，适合笔记本上的 3B–8B 原型。和 LangChain 对接时换 LLM 类即可，本地用 Ollama、上线再切 OpenAI / vLLM。

可用 Modelfile 固化 system prompt、temperature、上下文长度。

## LiteLLM：多提供商统一代理

托管 API \+ 自建 vLLM 并存时，LiteLLM 能做成统一 OpenAI 兼容入口，顺带 failover、负载和成本统计。多租户按套餐路由模型时特别省事。

## 可观测性

没有观测等于盲飞。至少看：延迟分位、Token、单次成本、错误率、缓存命中。用 LangChain 时 LangSmith 上手快；非 LangChain 可用 Langfuse / OpenLLMetry。

## 推理优化备忘

- 先算清 KV cache 占显存，避免上线才 OOM
- continuous batching 是 vLLM 默认优势，调 `--max-num-seqs` 匹配卡能力
- CPU offload 能塞更大模型，但延迟敏感场景别当主力
