做 AI SaaS，多租户要从推理路由、向量库到计费整层想清楚。内部工具的「单租户能跑」一到数据隔离、按租户定制、按量计费就会散架。

<Note>
  早期可以先共享基础设施。下面讲的是演进方向：合规和规模要求上来再加强隔离，过早隔离只会白白加复杂度。
</Note>

## 隔离模型

- **共享**：算力、库、向量库共用，靠元数据过滤和权限控数据
- **混合（多数生产更合适）**：算力共享，数据按租户拆（独立 collection / schema / 行级租户 ID）
- **独占**：企业合同、强监管场景，租户自有一套

无论哪种，这几层都要显式隔离：向量索引、会话历史、文件存储、用量归因。

请求进数据层之前，必须先解析出可信的 `tenant_id`（JWT claim 或 API Key 映射）。

## 按租户的 RAG

两种常见策略：

1. **一租户一 collection**：隔离强，运维多一点
2. **共享 collection \+ tenant\_id 过滤**：运维简单，但过滤必须由向量库强制，且要对 `tenant_id` 建 payload 索引

入库时每个 chunk 都要打上租户身份，不能事后补救。

## 请求路由与套餐

API 网关是统一控制点：鉴权、预算、按套餐选模型都在这里做，再进推理后端。例如 Free/Pro 走小模型，Enterprise 走更大模型；也可支持 BYOK 或租户自建 vLLM。

## 成本归因与限流

按请求记 `UsageEvent`（租户、用户、模型、prompt/completion tokens、成本）。PostgreSQL 够用；超高量可上 ClickHouse。预算建议软限制（提醒）\+ 硬限制（429），付费计划可考虑小幅超额缓冲。

## 异步与流式

文档入库、批量推理别卡在同步 HTTP 超时里——用任务队列（如 Celery）分优先级。聊天界面用 SSE/WebSocket 流式吐 token；单向推送优先 SSE，更简单好代理。

<Warning>
  数据隔离在不少行业是合规要求，不只是「最佳实践」。面向医疗/金融等企业客户前，隔离方案最好过合规评审。
</Warning>
