检索增强生成（RAG）在推理时用外部知识增强大语言模型。不再只依赖训练阶段学到的内容，RAG 从你自己的数据源取回相关文档并作为上下文提供——显著降低幻觉、支持领域问答，并让回答 grounded 在可核验内容上。

## RAG 流水线

RAG 分两个阶段：**索引**（一次性或周期性离线过程）与**查询**（每次用户请求触发的实时在线过程）。

<Steps>
  <Step title="索引阶段">
    原始文档被加载、切成块、转为向量嵌入，并连同元数据存入向量数据库。

    ```text
    Documents → Chunker → Embedding Model → Vector Store
    ```
  </Step>
  <Step title="查询阶段">
    用户查询用同一模型嵌入，用于检索最相关的块，可选地重排以提高精度，再与原始问题一起交给 LLM，合成 grounded 回答。

    ```text
    Query → Embedding Model → Retriever → Reranker → LLM → Answer
    ```
  </Step>
</Steps>

把两个阶段合在一起，完整数据流如下：

```text
                        ┌─────────────────────────────────────┐
  INDEXING              │                                     │
  ─────────             │  Document                           │
  Raw Docs              │     └─► Chunker                     │
     └─► Chunker        │            └─► Embedding Model      │
            └─► Embed   │                     └─► Vector Store│
                  └─► Store                                   │
                        └─────────────────────────────────────┘

                        ┌─────────────────────────────────────┐
  QUERYING              │                                     │
  ────────              │  User Query                         │
  User Query            │     └─► Embedding Model             │
     └─► Embed          │            └─► Retriever            │
            └─► Retrieve│                  └─► Reranker       │
                   └─► Rerank                    └─► LLM      │
                          └─► LLM                     └─► Answer
                                └─► Answer            │       │
                        └─────────────────────────────────────┘
```

<Note>
  RAG 系统质量首先受限于分块，其次是嵌入，再次是检索策略——甚至在 LLM 登场之前。请在索引流水线上重投入。
</Note>

### LangChain 中的基础 RAG 流水线

下面示例把 OpenAI embeddings、Qdrant 向量库与 GPT-4o 串成可用的 RAG chain：

```python title="basic_rag.py"
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import Qdrant
from langchain.chains import RetrievalQA

# Indexing
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vectorstore = Qdrant.from_documents(
    documents=docs,
    embedding=embeddings,
    url="http://localhost:6333",
    collection_name="knowledge_base"
)

# Retrieval + Generation
llm = ChatOpenAI(model="gpt-4o")
qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    retriever=vectorstore.as_retriever(search_kwargs={"k": 5})
)
result = qa_chain.invoke({"query": "What is our return policy?"})
```

## 何时使用 RAG

只要应用需要基于特定知识语料回答问题——尤其该语料会随时间变化——RAG 就是合适选择。

  <Card title="知识库" icon="book-open">

## RAG vs 微调

RAG 与微调都能让基座 LLM 适配你的需求，但解决的是不同问题。选错是 AI 工程中最常见的错误之一。

| 维度 | RAG | 微调 |
| --- | --- | --- |
| **知识更新** | ✅ 更新索引即可，无需重训 | ❌ 需要新的训练运行 |
| **Grounding / 引用** | ✅ 来源显式可审计 | ❌ 知识隐式在权重中 |
| **所需数据量** | ✅ 任意语料规模都可用 | ❌ 需要高质量标注样本 |
| **延迟** | ⚠️ 增加检索开销 | ✅ 单次推理调用 |
| **风格 / 语气控制** | ⚠️ 依赖提示工程 | ✅ 可直接微调到目标风格 |
| **行为改变** | ⚠️ 难以改基座行为 | ✅ 适合能力或格式变更 |
| **成本** | ✅ 无训练成本 | ❌ 训练算力昂贵 |

<Info>
  实践中，优秀的生产系统常两者结合：用微调管风格与指令遵循，再用 RAG 做领域事实 grounding。它们互补，而非互斥。
</Info>

**选 RAG，当**知识库很大、频繁更新，或需要透明引用与可审计性。

**选微调，当**需要改变模型行为或输出格式，或延迟极关键且无法接受检索开销。
