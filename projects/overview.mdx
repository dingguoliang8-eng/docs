## 这些项目背后的工程原则

这里的每个项目都由同一组原则塑造——它们来自反复试错，不是教条，而是可靠减少凌晨事故的模式。

<AccordionGroup>
  <Accordion title="可观测性优先：先埋点再优化" icon="chart-line">
    在能量化之前，我不碰性能。对 LLM 系统，这意味着用 LangSmith 追踪每条 chain 与 Agent 调用，在每步捕获 Token 数与延迟，并在写优化代码前先建仪表盘。优化黑盒是猜测。
  </Accordion>

  <Accordion title="评估驱动：上线前先建评估集" icon="flask">
    我吃过亏：没有 ground-truth 评估集就上线 RAG 改进，等于瞎飞。现在我会在写任何检索或生成逻辑前，先建标注评估集——问答对、期望工具调用、黄金输出。测不了就不发。
  </Accordion>

  <Accordion title="优雅降级：每次 AI 调用都可能失败；为此设计" icon="shield-halved">
    LLM API 会返回 429、超时，偶尔返回畸形 JSON。我构建的每个集成都有显式重试、回退模型与优雅错误响应。失败的 LLM 调用绝不该拖垮应用——应返回合理错误信息并记录失败供复盘。
  </Accordion>

  <Accordion title="可组合架构：小而可测的组件，而非巨型 chain" icon="cubes">
    400 行的 LangChain chain 不可测。我把流水线拆成最小有意义单元——retriever、reranker、提示格式化器、响应解析器——各自单元测试。组合发生在图层面（LangGraph），数据流显式可检视。
  </Accordion>
</AccordionGroup>

## 技术栈

这些项目共享同一技术底座。每个工具都是有意选择，并在生产中用到足以理解其权衡。

<CardGroup cols={2}>
  <Card title="后端" icon="server">
    **Python \+ FastAPI** 用于所有 API 面。FastAPI 的异步支持、自动 OpenAPI 文档与 Pydantic 集成，使其成为 LLM 密集后端的合适选择——你要处理流式响应与复杂请求校验。
  </Card>

  <Card title="编排" icon="sitemap">
    **LangChain \+ LangGraph** 用于 Agent 与流水线编排。LangChain 提供可组合积木；LangGraph 提供带 checkpoint 与中断支持的有状态、可循环 Agent 工作流。
  </Card>

  <Card title="向量存储" icon="magnifying-glass">
    **Qdrant** 做向量检索。原生支持 dense、sparse 与混合集合。过滤 API 足够表达按租户数据隔离，无需歪招。
  </Card>

  <Card title="推理" icon="microchip">
    **OpenAI GPT-4o / GPT-4o-mini** 做托管推理；需要数据主权或规模化控本时，经 **vLLM** 跑 **Llama 3 / Qwen 2.5** 自托管。
  </Card>

  <Card title="缓存与队列" icon="bolt">
    **Redis** 用于会话缓存、限流计数，并作为后台文档索引进程的 Celery 消息代理。快、简单、运维上为人熟知。
  </Card>

  <Card title="结构化数据" icon="table">
    **PostgreSQL** 存所有关系数据：用户、租户、用量记录、对话历史，以及生产中的 LangGraph checkpoint。JSONB 列承载半结构化 Agent 状态，无需单独文档库。
  </Card>
</CardGroup>
