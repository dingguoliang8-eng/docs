脱敏代表项目：近半年参与建设的 **端侧语音 Agent 智控平台**。目标是把「云端可运营的智控能力」和「设备侧实时语音 Agent」打成一条可上线闭环——管理配置、下发策略、跑会话、调工具、查知识，而不是三个互不相干的 Demo。

> 本文不出现公司名、产品品牌、客户与内部细节；只描述可公开的架构角色与工程取舍。

---

## 问题与目标

端侧语音场景要求低延迟与稳定会话；云端又要管设备、智能体、模型、知识库和团队权限。若两边各自为政，会出现：

- 配置无法按设备下发，现场只能改本地文件
- 助手能力停在单轮问答，接不上工具与知识库
- 权限与租户边界含糊，SaaS 化运营做不起来

目标是建成 **控制面 \+ 数据/会话面** 协同的平台：运营在智控台完成，实时语音在设备侧服务完成，契约清晰、可部署、可演进。

## 系统全景

```text
智控台前端 (Vue)
    ↕ HTTP
智控台后端 (Java / Spring)
  · 设备 / 智能体 / 模型 / 知识库
  · 团队权限与认证
  · 向设备侧下发 per-device 配置
    ↕ 配置拉取 / 管理 API
设备侧语音服务 (Python)
  · WebSocket 会话（一设备一连接）
  · VAD → ASR → LLM → TTS（或端到端语音路径）
  · 工具调用 / MCP / 插件
  · OTA、视觉等 HTTP 能力
```

## 我参与建设的部分

按「参与建设」表述（不夸大成单人主导全栈）：

- **智控台与后端**：设备/智能体/模型/知识库等业务域、团队权限与认证相关能力、与设备侧的配置下发契约
- **设备侧语音服务**：会话主路径与消息路由、ASR/TTS（及端到端语音）管线集成、工具/插件/MCP 调度、与智控台配置双模式协同
- **前端智控台**：管理界面与多环境/数据中心对接、权限相关交互
- **检索相关**：知识库与向量检索（含图像向量等场景）接入平台能力

## 关键设计

### 配置双模式

- **本地模式**：默认配置 \+ 本地覆盖，便于开发与单机联调
- **智控台模式**：连接时按设备拉取配置，密钥与环境覆盖不进默认模板

原则：默认结构可提交；密钥与现场覆盖隔离；协议字段与控制面保持一致。

### 实时会话管线

经典路径：`音频 → VAD → ASR → 意图/工具 → LLM → TTS → 回传`。另有端到端语音路径可选。会话主路径保持精简，新能力优先以 Provider / 插件 / 消息 Handler 扩展，避免在连接核心里堆 if-else。

### 工具与扩展

统一调度服务端插件、MCP、设备侧能力等 executor，让「能说话」升级为「能办事」。Schema、错误处理与超时是生产可用性的一部分，而不只是功能清单。

### 知识库与向量

控制面管理知识与模型；检索侧使用向量库（如 Qdrant）支撑文档/图像等召回，再进入生成或业务流程。多租户场景下过滤与隔离要在检索层显式设计。

### 权限分层

- 系统级权限（菜单/角色）
- 团队/资源级权限（业务数据隔离）

接口必须明确属于哪一层，避免「能登录就能看全部租户数据」。

## 上线阶段的工程取舍

功能基本闭环、进入上线时，优先级通常是：

1. **会话稳定性与延迟**：语音链路对首包和打断敏感，需要流式与异步/线程池边界清晰
2. **失败降级**：ASR/LLM/TTS 任一环失败不能拖垮整连接，要有重试、回退与可理解错误
3. **配置与密钥安全**：不把密钥写进默认可提交配置；下发契约变更要双边同步
4. **可观测性**：按连接/设备维度留下足够日志，否则线上只能重启

更多教训见 [经验总结](/notes/lessons-learned)。
