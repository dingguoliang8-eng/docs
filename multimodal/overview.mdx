Modern AI applications increasingly combine multiple modalities — text, speech, vision, and structured data — into unified systems. Rather than a single model answering text queries, production-grade AI now orchestrates pipelines where audio is transcribed, images are parsed, and language models reason over all of it together. This page gives you a map of the multimodal landscape and the engineering patterns that tie it together.

## Modality Overview

Each modality brings its own tooling, latency profile, and failure modes. Understanding what lives in each bucket helps you pick the right architecture before you write a line of code.

## Architecture Patterns for Multimodal Systems

Three dominant patterns emerge when you need to wire multiple modalities together. Each trades off flexibility, latency, and engineering complexity differently.

<AccordionGroup>
  <Accordion title="1. Sequential Pipeline" icon="arrow-right">
    Each modality is processed in order, with the output of one stage becoming the input of the next. A classic voice agent looks like:

    ```text
    Audio Input → ASR → Text → LLM → Text → TTS → Audio Output
    ```

    **Pros:** Simple to reason about, easy to swap individual components, each stage is independently testable.

    **Cons:** Latency compounds across stages. An error in an early stage (e.g., a bad transcription) propagates through the entire pipeline.

    Best for: voice agents, transcription workflows, audio summarization.
  </Accordion>

  <Accordion title="2. Unified Model" icon="cube">
    A single model natively handles multiple input modalities. Models like **GPT-4o** and **Gemini 1.5** accept text, images, and audio in a single API call and reason over all of them jointly.

    ```text
    Text + Image + Audio → Unified Model → Text / Audio Output
    ```

    **Pros:** Fewer moving parts, no alignment issues between stages, native cross-modal reasoning.

    **Cons:** Vendor lock-in, less control over individual modality quality, typically higher per-call cost.

    Best for: document Q&A with mixed content, real-time multimodal chat.
  </Accordion>

  <Accordion title="3. Modality Router" icon="code-branch">
    An upstream classifier detects the input modality and routes it to a specialized model optimized for that type.

    ```text
    Input → Classifier → [ASR Model | Vision Model | Text LLM] → Output
    ```

    **Pros:** Each modality gets the best-in-class model, allows fine-tuned specialists.

    **Cons:** Requires a reliable classifier upfront; ambiguous inputs (e.g., a PDF with text and images) need special handling.

    Best for: high-volume pipelines where you need to optimize cost and quality per modality.
  </Accordion>
</AccordionGroup>

## Key Engineering Challenges

<Warning>
  Multimodal systems multiply the surface area for bugs. A problem in any single modality — a misconfigured ASR model, an oversized image, a slow TTS call — can silently degrade the entire pipeline.
</Warning>

**Latency** is the most visible challenge. Each model in your pipeline adds inference time. For voice agents, users expect a response within roughly **500ms of finishing their sentence** — that budget has to be split across VAD, ASR, LLM first-token, and TTS. Streaming and parallelism are not optional; they are requirements.

**Alignment** means ensuring each stage produces output in the exact format the next stage expects. An ASR model that returns word-level timestamps is useless to an LLM expecting plain text unless you strip that metadata. A TTS model that expects short strings will choke on a 2,000-token LLM response unless you chunk it. Document every contract between stages explicitly.

**Error propagation** is especially dangerous in sequential pipelines. An ASR error — a misheard word or hallucinated phrase — becomes a factual error in your LLM's context. The LLM has no way to know the transcription was wrong. Mitigation strategies include confidence thresholds, VAD quality gates, and asking the LLM to flag uncertainty when its input seems garbled.

## Real-Time vs. Batch Processing

Not every multimodal workload has the same timing requirements. Choosing the right processing model upfront avoids costly rewrites later.

<AccordionGroup>
  <Accordion title="Real-Time (Streaming)" icon="bolt">
    Voice agents and live transcription require **streaming pipelines** where audio is processed as it arrives. Key techniques: chunked audio capture, streaming ASR with partial transcripts, sentence-level TTS so speech starts before the LLM finishes generating.

    Target: end-to-end latency **under 500ms** for a natural conversational feel.
  </Accordion>
  <Accordion title="Batch Processing" icon="database">
    Document understanding, invoice parsing, and video analysis can run asynchronously. You get to use larger, more accurate models (Whisper large-v3, GPT-4o with high-detail vision) without worrying about real-time latency budgets.

    Target: correctness and cost efficiency over speed.
  </Accordion>
</AccordionGroup>
