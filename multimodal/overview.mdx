现在的 AI 应用很少只剩文本。语音、图像、结构化数据常常要和语言模型串在一条链路里：音频转写、图像解析，再交给模型一起推理。这页先画地图，再讲怎么接。

## 各模态各自干什么

工具、延迟、失败模式都不一样。先分清，再选架构。

<CardGroup cols={2}>
  <Card title="文本" icon="file-lines">
    基础。大语言模型（LLM）处理与生成文本——本作品集其他章节有深入覆盖。文本是多数多模态流水线最终汇聚的「通用语」。
  </Card>

  <Card title="语音" icon="microphone">
    **ASR（自动语音识别）** 将音频转为文本。**TTS（文本转语音）** 将文本转回音频。**说话人分离** 把语音片段归属到具体说话人——对会议转写与多方语音 Agent 至关重要。
  </Card>

  <Card title="视觉" icon="eye">
    视觉模型处理**图像理解**（描述、VQA、分类）、**文档解析**（OCR、表格抽取、表单理解）与**视频分析**（帧级推理、时序理解）。
  </Card>

  <Card title="组合" icon="layer-group">
    组合模态解锁新应用类别：**语音 Agent**（ASR → LLM → TTS）、**多模态聊天机器人**（文本 \+ 图像输入）、**含图文档问答**（含图表、示意图与混合版式的 PDF）。
  </Card>
</CardGroup>

## 多模态系统的架构模式

需要把多种模态接在一起时，有三种主流模式。各自在灵活性、延迟与工程复杂度上权衡不同。

<AccordionGroup>
  <Accordion title="1. 顺序流水线" icon="arrow-right">
    各模态按序处理，上一阶段输出成为下一阶段输入。经典语音 Agent 形如：

    ```text
    Audio Input → ASR → Text → LLM → Text → TTS → Audio Output
    ```

    **优点：** 易于推理、易替换单组件、各阶段可独立测试。

    **缺点：** 延迟跨阶段累加。早期错误（如坏转写）会贯穿整条流水线。

    最适合：语音 Agent、转写工作流、音频摘要。
  </Accordion>

  <Accordion title="2. 统一模型" icon="cube">
    单个模型原生处理多种输入模态。如 **GPT-4o** 与 **Gemini 1.5** 可在一次 API 调用中接受文本、图像与音频，并联合推理。

    ```text
    Text + Image + Audio → Unified Model → Text / Audio Output
    ```

    **优点：** 活动部件更少、无阶段对齐问题、原生跨模态推理。

    **缺点：** 供应商锁定、对单模态质量控制更少、通常单次调用成本更高。

    最适合：混合内容的文档问答、实时多模态聊天。
  </Accordion>

  <Accordion title="3. 模态路由器" icon="code-branch">
    上游分类器检测输入模态，并路由到针对该类型优化的专用模型。

    ```text
    Input → Classifier → [ASR Model | Vision Model | Text LLM] → Output
    ```

    **优点：** 每种模态可用最佳模型，允许微调专家。

    **缺点：** 需要可靠的前置分类器；模糊输入（如含文本与图像的 PDF）需特殊处理。

    最适合：需要按模态优化成本与质量的高流量流水线。
  </Accordion>
</AccordionGroup>

## 关键工程挑战

<Warning>
  多模态系统放大了出 bug 的表面积。任一模态的问题——ASR 配置错误、过大图像、缓慢 TTS——都可能静默拖垮整条流水线。
</Warning>

**延迟**是最显眼的挑战。流水线中每个模型都增加推理时间。对语音 Agent，用户期望在说完后约 **500ms 内**得到响应——该预算要分给 VAD、ASR、LLM 首 Token 与 TTS。流式与并行不是可选项，而是硬需求。

**对齐**意味着确保每阶段输出格式正是下一阶段所期望的。返回词级时间戳的 ASR 对期望纯文本的 LLM 无用，除非你剥掉元数据。期望短字符串的 TTS 会噎在 2000 Token 的 LLM 响应上，除非你做切分。请显式记录阶段之间的契约。

**错误传播**在顺序流水线中尤其危险。ASR 错误——听错词或幻觉短语——会变成 LLM 上下文中的事实错误。LLM 无法知道转写是错的。缓解策略包括置信度阈值、VAD 质量门控，以及在输入看起来乱码时让 LLM 标记不确定性。

## 实时 vs 批处理

并非每种多模态负载都有相同的时效要求。事先选对处理模型，可避免日后昂贵的重写。

<CardGroup cols={2}>
  <Card title="实时（流式）" icon="bolt">
    语音 Agent 与实时转写需要**流式流水线**，音频边到边处理。关键技巧：分块音频采集、带部分转写的流式 ASR、句级 TTS，以便 LLM 尚未生成完就开始播报。

    目标：端到端延迟 **低于 500ms**，以获得自然对话感。
  </Card>

  <Card title="批处理" icon="database">
    文档理解、发票解析与视频分析可异步运行。可用更大、更准的模型（Whisper large-v3、高细节视觉的 GPT-4o），而不必担心实时延迟预算。

    目标：正确性与成本效率优先于速度。
  </Card>
</CardGroup>
